| Letra Tero es un marketplace uruguayo que vende accesorios, ropa, comida y vehículos livianos. Lo construyó un equipo pequeño y funciona: tiene tienda, carrito, checkout, órdenes y un panel de administración, repartidos en seis microservicios con su base de datos y su Redis. El problema no es lo que hace, sino dónde y cómo corre. Hoy Tero se ejecuta únicamente con docker compose en las computadoras del equipo de desarrollo. No existe un ambiente en la nube, no hay pipelines y nadie puede decir con certeza qué versión del código está corriendo. Cada demostración implica que alguien levante los contenedores a mano y confíe en que todo arranque. Un fondo de inversión regional quiere financiar la expansión de Tero, pero condicionó el cierre de la ronda a una auditoría técnica. Los primeros días de Diciembre, una firma auditora visitará la empresa con un checklist de controles. Tero debe poder demostrar cada uno con evidencia concreta. Si no los cumple, la ronda se posterga. Antes de la visita formal, el auditor revisó el repositorio y dejó estas observaciones preliminares, que no son exhaustivas: Las contraseñas de la base de datos y las credenciales del panel de administración están escritas en archivos del repositorio. Todas las imágenes de contenedor se construyen en un solo paso sobre imágenes base completas, y los procesos corren como administrador (root) dentro del contenedor. La base de datos y Redis están publicados en puertos de la máquina anfitriona. No hay pruebas automatizadas, ni análisis de código ni de dependencias. No hay forma de saber qué versión se está ejecutando ni de repetir un despliegue de la misma manera dos veces. Algunos servicios ya exponen métricas, pero nadie hace la recolección ni las mira. La empresa los contrata como equipo consultor DevOps. El objetivo no es aprobar la auditoría con maquillaje: Tero no tiene cultura DevOps ni un equipo de infraestructura propio, y su gente tendrá que operar lo que ustedes construyan una vez terminada la consultoría. Por eso el auditor no sólo verificará que los controles se cumplan, sino que alguien más pueda entenderlos, repetirlos y mantenerlos. Entrega  A continuación, se detallan los aspectos que deberá contemplar la solución entregada. Cada sección define requerimientos mínimos obligatorios; el equipo es libre de superar dichos mínimos. Planificación y Seguimiento Utilizar *Kanban* o *Scrum* para planificar y hacer seguimiento de las tareas identificadas por el equipo. Documentar mediante capturas de pantalla el estado del tablero en al menos tres momentos distintos del proyecto (inicio, mitad y cierre), evidenciando la evolución del trabajo. El tablero debe reflejar la totalidad de las tareas del proyecto, incluyendo las de infraestructura, seguridad, testing y observabilidad.  Integración y Entrega Continua (CI/CD) Desarrollar *pipelines* de CI/CD para al menos tres ambientes: Dev, Test y Prod. Cada pipeline debe contener como mínimo las siguientes etapas/fases: Build / compilación de artefactos. Ejecución de pruebas automatizadas. Análisis de calidad de código (ver sección 4). Análisis de seguridad (ver sección 5). Publicación de imagen de contenedor (ver sección 3). Despliegue al ambiente correspondiente. Implementar *quality gates* entre ambientes: ningún artefacto debe promoverse al siguiente ambiente si no cumple los umbrales definidos de calidad y seguridad. El pipeline debe ser reproducible y estar completamente definido como código (YAML u otro formato de definición declarativa).  Containerización y Despliegue Optimizar la construcción de imágenes de contenedor aplicando buenas prácticas, por ejemplo: Uso de imágenes base mínimas (distroless, alpine o similares). Construcción multi-stage para reducir el tamaño final de la imagen. Usuario no-root dentro del contenedor. *.dockerignore* adecuado. Publicar las imágenes en un container registry (ECR, Docker Hub, GHCR u otro). Desplegar los contenedores en un servicio de orquestación en nube (AWS ECS, EKS u equivalente en Azure/GCP).  Testing y Calidad Implementar *al menos uno* de los siguientes tipos de testing: Pruebas funcionales / de integración entre microservicios (Postman/Newman, REST-assured, Pact, Selenium, etc.). Pruebas de carga y rendimiento (k6, JMeter, Locust, etc.). (escribir un par de tests solamente) Integrar *una* herramienta de análisis de código estático (SonarQube, ESLint, Semgrep, o similar) en el pipeline de CI. Definir umbrales de calidad (coverage mínimo, número máximo de code smells, etc.) que actúen como quality gate. Elaborar un informe\* con los resultados obtenidos, hallazgos significativos y recomendaciones de mejora.(\* el informe no es más que un párrafo en la documentación que exprese la interpretación de los resultados).  DevSecOps Integrar en el pipeline de CI *una* herramienta de Software Composition Analysis (SCA) que analice las dependencias de los microservicios en busca de CVEs conocidos. Ejemplos de herramientas: Trivy (modo filesystem), Snyk, OWASP Dependency-Check. Definir un quality gate que bloquee el pipeline ante vulnerabilidades de severidad CRITICAL o HIGH sin parche disponible. Escanear cada imagen de contenedor construida antes de publicarla en el registro. Ejemplos de herramientas: Trivy (modo image), Anchore Grype, Clair. Integrar *al menos una* herramienta de Static Application Security Testing (SAST) en el pipeline. Ejemplos de herramientas: Semgrep, Bandit (Python), GoSec (Go), NodeJsScan, SonarQube. Reportar los hallazgos y documentar las remediaciones aplicadas o las excepciones justificadas. Ningún secreto (contraseña, API key, token, connection string) debe estar hardcodeado en el código fuente ni en los archivos de configuración del repositorio. (.gitignore frenar el .env por ejemplo) Integrar en el pipeline *un* detector de secretos expuestos (git-secrets, detect-secrets, TruffleHog, Gitleaks u otros) que falle el build si detecta credenciales en el código.  Control de Versiones Almacenar todo el código (aplicación, pipelines, IaC, configuración) en repositorio/s Git. Implementar una estrategia de ramificación claramente definida. Opciones sugeridas: Git Flow (ramas main, develop, feature/\*, release/\*, hotfix/\*). Trunk-Based Development con feature flags. GitHub Flow (main \+ feature branches \+ PRs). Justificar la elección de la estrategia en función de las características del equipo y del contexto del proyecto. Demostrar colaboración efectiva mediante Pull Requests con revisiones de código entre integrantes del equipo (mínimo dos PRs documentados con comentarios de revisión). Las ramas de feature no deben fusionarse a main/develop sin aprobación de al menos un revisor distinto al autor (revisar por ejemplo Branch Protection Rules).  Infraestructura como Código (IaC) Implementar toda la infraestructura como código utilizando Terraform (salvo el bucket del estado de Terraform). El código de IaC debe cumplir los siguientes estándares: Modularización adecuada: al menos *un* módulo reutilizable (ej: módulo de red, de contenedores, de base de datos). Variables parametrizadas por ambiente: usar archivos *.tfvars* diferenciados para Dev, Test y Prod. Outputs relevantes documentados con descripción. Manejo seguro de secretos: no almacenar valores sensibles en el estado de Terraform sin cifrar. Estado remoto: usar un backend remoto (S3, Terraform Cloud u otro) para el archivo de estado. Servicios Serverless (*elegir al menos uno*): AWS Lambda para automatizaciones y/o procesamiento de eventos: alertas automáticas, análisis de logs de seguridad, notificaciones de vulnerabilidades, rotación de secretos, etc. API Gateway para gestión de acceso y seguridad a APIs: rate limiting, autenticación, WAF básico. El servicio serverless debe integrarse con el resto de la arquitectura y tener un propósito claramente definido. Se valorará especialmente que el propósito esté relacionado con seguridad u observabilidad.  Observabilidad Implementar una solución de monitoreo que permita tener visibilidad del estado del sistema en producción. Recolectar métricas de infraestructura (CPU, memoria, red) o de aplicación (latencia, tasa de errores, throughput) para los microservicios desplegados. Centralizar los logs de todos los servicios en una plataforma única, con formato estructurado que permita búsquedas y filtros. Configurar al menos *1 dashboard* con métricas relevantes para la operación del sistema. Establecer al menos *2 alertas* que cubran disponibilidad, rendimiento, seguridad y/o uso de recursos. Cada alerta debe tener definida su condición de disparo (trigger) y un procedimiento básico de respuesta. Herramientas sugeridas (no excluyentes): CloudWatch, Prometheus, Grafana, Loki, Open Telemetry u otras equivalentes.  Documentación Crear un README.md completo con instrucciones de despliegue, configuración de variables de entorno y pre-requisitos. Generar los siguientes diagramas: Diagrama de arquitectura general del sistema. Flujo completo del pipeline CI/CD con las etapas de seguridad integradas. Estrategia de Git (branching model) adoptada. Documentar las decisiones de diseño más relevantes (Architecture Decision Records o formato libre) y las lecciones aprendidas del proyecto.
